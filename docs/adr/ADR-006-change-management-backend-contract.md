# ADR-006 — Change management backend contract

- Status: Accepted (F2.0 architecture)
- Date: 2026-08-30
- Related: [ADR-002](./ADR-002-backstage-change-onramp.md), [ADR-003](./ADR-003-provider-agnostic-change-management.md)

## Context

F1.4 delivered a provider-neutral GMUD frontend with `ChangeManagementApi` and a mock implementation. **F2.0 (ADO commit `b2bed17`)** adds the backend contract scaffold: `ChangeManagementService`, `IChangeManagementProvider`, HTTP routes, RBAC, and unit tests — using an in-memory fake provider only. There is still **no durable persistence**, **no ITSM integration**, and **no frontend wiring**.

F2.0 defines the backend architecture required to support:

1. create a change;
2. retrieve a change by `changeId`.

List/search, ITSM providers, workflow engines, and Azure DevOps integration are explicitly out of scope.

## Decision

### Service boundary

```text
Backstage GMUD frontend
        |
        v
Frontend ChangeManagementApi          (F2.1 wiring)
        |
        v
POST/GET /api/change-management/changes
        |
        v
ChangeManagementService
        |
        v
IChangeManagementProvider
        |
        +-- FakeChangeManagementProvider   [F2.0 test-only]
        +-- Development provider           [F2.1]
        +-- SharePoint / Jira / ServiceNow [future/optional]
```

The canonical Change Management domain remains independent from Azure DevOps, pipelines, deployments, Teams, CAB, and ITSM schema.

### Layered contracts

| Layer | Purpose | Examples |
|---|---|---|
| Transport DTO | HTTP request/response | `CreateChangeHttpRequest`, `CreateChangeHttpResponse` |
| Domain command | Post-validation + enrichment | `CreateChangeCommand` |
| Public change model | Provider-neutral persisted/read shape | `Change` |
| Internal provider metadata | Adapter boundary only | `ProviderReference` |

Transport DTOs must not be blindly copied from frontend types. The backend contract is authoritative.

### Trusted create request contract

**Accepted from the client (HTTP POST body):**

| Field | Source |
|---|---|
| `targetRef` | User-selected catalog target |
| `classification` | User form |
| `title` | User form |
| `summary` | User form |
| `requestedWindow` | User form (`date`, `startsAt`, `endsAt` — no timezone) |
| `risk` | User form |
| `rollbackPlan` | User form |
| `evidence` | User form (F2.0 accepts `[]` only) |

**Derived server-side (not trusted from client):**

| Field | Source |
|---|---|
| `requestedBy` | Backstage authenticated identity (`userInfo.userEntityRef`) |
| `ownerRef` | Catalog `spec.owner` resolved from `targetRef` |
| `systemRef` | Catalog `spec.system` resolved from `targetRef` |
| `changeId` | Generated by `ChangeManagementService` before provider write |
| `status` | Always `submitted` on create (no draft persistence) |
| `createdAt` | Server clock (UTC ISO 8601) |
| `requestedWindow.startsAtUtc` / `endsAtUtc` | Normalized from form + configured timezone |

**Rejected from canonical public model (must never appear):**

`repositoryId`, `pipelineId`, `buildId`, `deploymentId`, `environmentId`, `adoApprovalId`, `teamsUserId`, `provider`, `sharePointItemId`, `jiraIssueKey`, `serviceNowSysId`, and similar provider/execution fields.

### Requester identity (anti-spoofing)

The frontend currently sends `requestedBy`, but the backend **must not** treat it as authoritative.

- `CreateChangeHttpRequest` excludes `requestedBy`.
- If legacy clients send `requestedBy`, it is ignored.
- `CreateChangeCommand.requestedBy = authenticatedActor.userEntityRef`.

This prevents user A submitting a request claiming to be user B.

### Owner and system context

The backend resolves `ownerRef` and `systemRef` from `targetRef` via the Catalog API using the caller's credentials.

- Frontend-supplied `ownerRef` / `systemRef` are not accepted in the HTTP DTO.
- UI may continue to display catalog-derived context read-only until F2.1 frontend migration.
- If the target entity cannot be read → `404` / validation error.
- **F2.0 limitation:** `targetRef` must reference a Catalog **Component** entity (F1.3 scope). System/Resource targets require a future ADR.

### Minimal `ChangeStatus`

Only **`submitted`** is valid in F2.0.

The F1 mock returned `draft | submitted`. Draft persistence does not exist; `draft` is removed from the backend contract.

Future workflow states (`approved`, `rejected`, `executed`, etc.) belong to later slices — not F2.0.

### `changeId` ownership

**Service-owned canonical ID (preferred):**

1. `ChangeManagementService` generates `changeId` (format concept: `CHG-{YYYY}-{seq}`).
2. Provider receives the canonical `Change` including `changeId`.
3. Provider returns only `ProviderReference` (external correlation).
4. On provider failure, the ID is **discarded** — never returned to the client.

This preserves provider replaceability versus using an external ITSM ID as the canonical identifier.

Distributed sequence generation is deferred to F2.1; F2.0 uses a test-only in-memory sequence in `FakeChangeManagementProvider`.

### Provider contract

```typescript
interface IChangeManagementProvider {
  create(change: Change): Promise<{ providerReference: ProviderReference }>;
  get(changeId: string): Promise<
    { change: Change; providerReference: ProviderReference } | undefined
  >;
}
```

**Tradeoff:** the provider operates on the canonical `Change` model rather than a duplicated `ProviderCreateRequest`. This reduces field drift and simplifies adapter swaps.

Provider-specific metadata lives in `ProviderReference`:

```typescript
ProviderReference {
  providerKey: string;
  externalId?: string;
  externalUrl?: string;
}
```

`ProviderReference` is **internal** — not exposed in the public `Change` HTTP response in F2.0.

### HTTP contract

| Method | Path | Permission |
|---|---|---|
| `POST` | `/api/change-management/changes` | `change-management.change.create` |
| `GET` | `/api/change-management/changes/:changeId` | `change-management.change.read` |

**POST headers:** optional `Idempotency-Key` (recommended; persistent handling in F2.1).

**Responses:**

| Status | Code | When |
|---|---|---|
| 201 | — | Create succeeded `{ changeId, status: "submitted" }` |
| 200 | — | GET succeeded `{ change: Change }` |
| 400 | `VALIDATION_ERROR` | Invalid input |
| 401 | `UNAUTHORIZED` | Missing credentials |
| 403 | `FORBIDDEN` | Permission denied or read scope |
| 404 | `NOT_FOUND` | Unknown `changeId` |
| 409 | `CONFLICT` | Idempotency key reused with different payload |
| 503 | `PROVIDER_UNAVAILABLE` | Provider write/read failure |
| 500 | `INTERNAL_ERROR` | Unexpected failure |

Error envelope:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Human-safe message",
    "details": { "field": "reason" }
  }
}
```

Raw provider exceptions must not leak to clients.

### Authorization / RBAC

Permissions (Backstage Permission Framework):

- `change-management.change.create` — action: `create`
- `change-management.change.read` — action: `read`

Registered via `coreServices.permissionsRegistry.addPermissions()`.

**Role assignments (F2.0):**

| Role | create | read |
|---|---|---|
| `contributor` | yes | yes |
| `template_executor` | yes | yes |
| `platform_admin` | yes | yes |
| `authenticated` | no | no |

Enforced in routes via `coreServices.permissions.authorize()`.

**GET read scope (minimal F2.0):**

- `platform_admin` → any change
- Otherwise → `change.requestedBy === actor.userEntityRef` **OR** actor `ownershipEntityRefs` includes `change.ownerRef`

Team-wide / all-changes listing scope is deferred to F3.

### Validation (backend)

Independent from frontend validation. Minimum invariants:

- `targetRef` required; valid entity ref; kind `Component` (F2.0)
- `classification` ∈ `{ normal, emergency }`
- `title` trimmed, 3–200 chars
- `summary` trimmed, 10–5000 chars
- `requestedWindow`: valid date (`YYYY-MM-DD`), times (`HH:mm`), **endsAt > startsAt**
- `risk` ∈ `{ low, medium, high }`
- `rollbackPlan` min 10 chars trimmed
- `evidence`: array; F2.0 accepts empty array only

### Timezone semantics

- Frontend sends date + time **without timezone**.
- Backend interprets using `changeManagement.defaultTimezone` in app-config (default: `America/Sao_Paulo`).
- Domain model stores `startsAtUtc` / `endsAtUtc` as ISO 8601 UTC strings plus the configured `timezone` label.
- Per-system or multi-timezone resolution is **unresolved** — deferred to future ADR if needed.

### Idempotency

Duplicate POST handling via optional `Idempotency-Key` header:

- Same key + same payload hash → return existing `{ changeId, status }`
- Same key + different payload → `409 CONFLICT`
- No key → each POST creates a new change (acceptable in dev; key recommended before production)

F2.0 uses in-memory idempotency in the fake provider; durable storage in F2.1.

### Failure semantics

Fail-closed:

```text
validate → authorize → enrich → generate changeId → provider.create
  ├─ success → 201 with changeId
  └─ failure → 503 PROVIDER_UNAVAILABLE; changeId NOT returned
```

No saga, no durable "failed" record in F2.0.

### Observability

Structured logs (never log full rollback plans, evidence content, tokens, or credentials):

| Event | Fields |
|---|---|
| `change.create.requested` | targetRef, actor, idempotencyKey? |
| `change.create.succeeded` | changeId, providerKey |
| `change.create.failed` | error code, providerKey |
| `change.read` | changeId, actor, outcome |
| `validation.failed` / `auth.denied` | code, actor |

Correlation via `changeId` and Backstage request logger.

### Test strategy (F2.0)

**Domain / service:**

- Authenticated actor becomes `requestedBy`; spoofing prevented
- Owner/system enrichment from catalog
- Classification and window validation
- Provider failure propagation; no fake `changeId`
- Provider-neutral public output
- Service-owned `changeId`
- Idempotency behavior

**Architecture guards:**

- No forbidden fields in canonical types
- Frontend does not import provider implementation

### Frontend compatibility (question #15)

**Can a provider swap occur without changing the frontend create form?**

**Yes.** The form continues to collect business fields (`targetRef`, classification, title, summary, window, risk, rollback). Removing `requestedBy` / `ownerRef` / `systemRef` from the HTTP payload is a transport migration (F2.1) — the UI display of requester/responsável remains unchanged.

### Intentionally excluded (F2.0)

- Real SharePoint / Jira / ServiceNow providers
- Azure DevOps / pipeline / deployment correlation implementation
- Teams approvals, CAB scheduling, workflow engine
- Draft persistence, list/search UI, detail page
- Attachments, evidence upload, notifications
- Automatic execution

## Architecture questions (explicit answers)

| # | Question | Answer |
|---|---|---|
| 1 | Trusted create contract | `CreateChangeHttpRequest` — user-editable fields only |
| 2 | Frontend fields | targetRef, classification, title, summary, requestedWindow, risk, rollbackPlan, evidence |
| 3 | Server-derived fields | requestedBy, ownerRef, systemRef, changeId, status, timestamps, UTC window |
| 4 | Who generates changeId | ChangeManagementService (before provider write) |
| 5 | Minimal ChangeStatus | `submitted` only |
| 6 | Provider metadata isolation | Internal `ProviderReference`; not in public `Change` |
| 7 | Provider failures | HTTP 503 `PROVIDER_UNAVAILABLE`; fail-closed |
| 8 | Authorization | Permission Framework + route-level `authorize()` |
| 9 | Requester spoofing | Server identity only; client `requestedBy` ignored |
| 10 | Duplicate POSTs | Optional `Idempotency-Key` header |
| 11 | Timezone | Configured default timezone → UTC storage |
| 12 | getChange returns | Public `Change` model; 404/403 as appropriate |
| 13 | Excluded domain fields | All pipeline/ITSM/Teams/ADO-specific IDs |
| 14 | Provider swap impact | New `IChangeManagementProvider` + config only |
| 15 | Frontend form unchanged on swap | Yes |

## Consequences

- Positive: Clean seams for F2.1 development provider and future ITSM adapters.
- Positive: Audit-grade requester identity without trusting the client.
- Positive: Catalog-authoritative ownership context.
- Trade-off: Frontend transport DTO diverges from F1.4 payload until F2.1 wiring.
- Trade-off: In-memory fake provider and idempotency are non-production.

## Recommendation for F2.1

1. Development provider with durable persistence (SQLite/Postgres)
2. Real `changeId` sequence
3. Wire frontend `ChangeManagementApi` to backend via discovery + fetch
4. Remove `requestedBy` / `ownerRef` / `systemRef` from frontend POST payload
5. Persistent idempotency keys
6. **STOP** before SharePoint/Jira/ServiceNow
